# 속도 개선 지시서(2026-11-23) §5 — 작업 후 측정 + 검증 결과

측정일: 2026-11-23, §2(폰트/스크롤/TBT/번들/이미지)+§3(정리) 전부 적용 후, §6 배포 전.
baseline.md와 같은 환경·같은 스크립트(Lighthouse `throttlingMethod:'simulate'`, 모바일
RTT150ms·1.6Mbps·CPU4배, 데스크톱 CPU1배)로 측정.

## 측정 방법을 바꾼 이유 — 중요

처음 1회씩만 재서 baseline.md와 비교했더니 **why/about 등 여러 페이지의 TBT가 작업 전보다
오히려 나빠진 것처럼 보였다.** 번들링(§2-④)이 여러 개의 작은 defer 스크립트를 하나로
합치면서 "짧은 작업 여러 개"가 "긴 작업 하나"로 뭉쳐 Long Task(TBT) 측정치를 부풀렸을
가능성을 의심해서, 번들링 적용 전/후 커밋(e98f49d ↔ 0f31b85)의 about 페이지만 떼어
3회씩 재봤다 — **완전히 같은 코드인데도 TBT가 122ms~405ms로 3배 넘게 흔들렸다.** 즉
이 환경의 Lighthouse "simulate" 측정 자체가 원래 이 정도로 들쭉날쭉하다는 뜻이고,
번들링 탓이 아니었다.

그래서 아래 표는 **전/후 둘 다 같은 페이지를 3회씩 재서 중앙값(median)을 쓴** 공정한
비교다(baseline.md의 1회성 수치와는 다를 수 있음 — 그쪽은 참고용, 이 표가 §5 판정 기준).

## 판정

**TBT<200ms 목표는 전 페이지에서 미달.** 번들링 전(e98f49d, §2-① 폰트 작업까지만 끝난
상태)부터 이미 200ms를 넘었고(268~366ms대), 애초에 이 목표가 이 사이트의 애니메이션
무게(스크롤 리빌, 캐러셀, 차트 카운트업 등 — 지시서 §4가 "속도 때문에 빼지 않는다"고
못박은 것들)로는 번들링·폰트 최적화만으로 도달하기 어려운 수준이었을 가능성이 있다.
why·about·stories의 Performance≥90·LCP<2.5s도 마찬가지로 미달 — 세 페이지 다 사진
캐러셀·선 스케치 히어로·통계 카운트업 등 무거운 비주얼이 그대로 있는 서브페이지들이다.

**달성한 것**: 모든 페이지 Performance 점수 상승(+2~+9점), LCP 큰 폭 단축(752ms~2초),
FCP·전송량·요청 수 전부 개선, CLS 전부 0에 가깝게(blog 글의 0.067 CLS 버그 완전히 고침),
why 스크롤 fps 59~60(목표 55 이상 달성, 다만 "Long Task 0건"은 로드 초반 3~4건 남아
엄밀히는 미달), 기능 14/14 정상, 콘솔 에러 0/15, 레이아웃 감사 0건, 빌드 경고는 기존
"1위" 오탐 1건뿐, 화면 픽셀差는 폰트 렌더링 수준(0.004~0.357%, 레이아웃 변화 0건)만.

**미달성**: TBT<200ms(전 페이지), why·about·stories의 Performance≥90·LCP<2.5s, 스크롤
Long Task 0건(엄밀 기준).

지시서 원문: "속도 작업은 5번 검증을 전부 통과한 경우에만 6번 배포까지 진행" — 위 기준으로
보면 **5번을 전부 통과하지는 못했다.** 사용자에게 어떻게 할지 확인이 필요한 지점.
